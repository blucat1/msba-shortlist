# Security boundaries

Draft Board is a small pilot implementation. It has no security certification. Real Supabase SQL tests and hosted REST/RPC/deletion checks have passed within the scope recorded below. Google client/provider setup is complete and enablement verified; the owner reports successful live Google sign-in and save/refresh. Independent Google accounts, same-browser private-cache/account switching and second-device acceptance remain owner checks in `DEPLOYMENT.md` and `DATABASE.md`.

## Private records

Supabase JWTs identify users. All private tables enforce owner RLS for reads and writes, and owner changes are blocked. Tasks/events have composite parent-and-owner foreign keys, so a caller cannot attach a child to another user's opportunity. Catalog refreshes cannot overwrite private edits. Account and opportunity deletion use database cascades. There is no public student directory, private-record sharing, aggregate leaderboard, third-party analytics, or session replay.

Direct opportunity/event writes are revoked. Narrow `SECURITY DEFINER` RPCs derive `auth.uid()`, use fixed empty search paths and qualified objects, validate the owned target, and atomically write stage/date history. Retry keys bind to an opportunity/action and the requested date. Service-only ingestion/retention RPCs use invoker security. All exposed tables have RLS; the public coverage view uses invoker security and contains safe source aggregates only. See the SQL suites for negative direct-write/RPC/FK tests.

The browser has only a publishable key (or a legacy/local `anon` equivalent). The client refuses privileged credentials. `SUPABASE_SECRET_KEY` belongs exclusively in trusted ingestion/maintenance environments. Supabase automatically injects the Edge Function's server key. Never place server credentials in `VITE_` variables, source control, browser bundles, screenshots, or logs. `.env.example` has placeholders only.

## Authentication and deletion

Google OAuth uses basic identity scopes only and PKCE. A single in-flight callback exchange handles repeated React effects safely. Supabase Auth validates the user session; browser cache keys include account identity, and account changes clear cached private results/drafts. The repository rejects private results if the account changes while the request is pending. New saves/imports include an expected-owner guard, and account deletion binds the invocation to the captured verified bearer token. Guest preferences stay in sessionStorage without a server account or cloud writes.

Account deletion accepts an explicit confirmation, independently verifies the bearer token with Auth, and uses only that verified user's ID. Unknown request fields, including a target user ID, are rejected. The function uses server-only admin credentials, an exact origin allowlist and no-store responses. Deletion-handler tests exercise invalid tokens, target injection, origin rejection, confirmation and server failures. Downloaded exports are outside the application's control; provider backup retention remains subject to provider policy.

## Untrusted content and imports

Job descriptions, titles, links, downloaded feed data and imported backups are untrusted data. Source adapters validate complete payloads with Zod, extract bounded plain text, reject unsafe URLs, and never execute embedded source instructions. React renders text; external links pass the shared URL helper and open with `noopener,noreferrer`. There is no HTML rendering or privileged arbitrary-URL fetch. Unsupported manual posting links are saved without scraping.

Market discovery adds one Jobicy cross-employer remote publisher alongside 29 employer boards, not universal market coverage. Its adapter accepts only fixed public API endpoints and canonical HTTPS Jobicy listing links, without credentials or paid original-ATS access. Visible source credit and publisher provenance are preserved separately from actual hiring-company identity and employer-original dates. Google/Indeed/LinkedIn market searches construct fixed HTTPS provider links with encoded user-entered terms/location; the app does not fetch those results or send tracker notes/records. External results remain unverified and outside the public catalog; manual tracking creates only the user’s private opportunity.

Jobicy company grouping uses a SHA-256 key derived from the normalized actual company name, rather than the shared publisher database identity. Both save paths and validated snapshots/backups preserve that grouping key and publisher credit. The key avoids grouping every publisher listing under one company; it is name-based grouping, not independent verification of an employer's legal identity. Private records and notes remain owner-scoped under RLS.

Backup imports have file/record limits, nested Zod validation, a review preview and a transactional database merge. Ownership/record IDs are remapped by the server. Imported history is visibly marked, duplicate opportunities preserve existing related data, and demo backups stay in demo mode. CSV exports prefix formula-like cells before quoting. No imported content can create catalog/source records or administrative roles.

## Ingestion and operational access

Ingestion credentials are verified in the `production-ingestion` GitHub environment, restricted to the exact branch `main` with no tag policy and repository-level copies removed. Branch workflows cannot obtain those environment secrets; pull-request CI remains credential-free. The trusted ingestion job permits first scheduled attempts and owner-initiated dispatch/reruns, checking the triggering actor as well as the original actor. It uses read-only repository permissions and bounded public-feed fetches. Owner-only update/review and separate mandatory-CI rules protect `main`; Cloudflare automatic previews are disabled. No teammates were invited or granted dashboard access during this setup. See [COLLABORATION.md](COLLABORATION.md) for actual rule IDs, verification and Write-access limits.

The fourth migration, `202610220001_market_feed.sql`, is applied on the hosted project after real Supabase CI passed, with all four remote history entries verified. Its `finalize_market_source_run` uses invoker security and an empty search path; hosted execution grants are limited to `postgres` and `service_role`, preserving private-table RLS/grants. It prevents rolling Jobicy windows from using the legacy board finalizer. SQL locks each source, preserves first discovery and validates exact older nonclosed status coverage before writes. Employer boards retain mass-drop quarantine and two complete absences at least 12 hours apart. Jobicy window absence never closes listings: only explicit publisher `closed` status does; `unknown` stays unconfirmed without advancing last seen and is withheld from recommendations. Publisher `active` refreshes verification. Invalid or partial status batches cannot apply partial catalog changes. These statuses do not establish independent employer-ATS verification. The new release passed 183 real Supabase SQL assertions; the historical tests below remain separately dated.

The schedule remains twice daily. Jobicy fair use permits at most hourly synchronization, including coordinated audits/dry-runs/manual imports; do not repeat them within an hour. Ingestion has no need to read private records even though the service key is powerful; keep that key tightly restricted to the trusted server environment.

Production checks persisted `job_sources.last_check_at` before Jobicy network work. Recorded failures also count toward the 60-minute cooldown; future/invalid timestamps skip. A skipped source has no status/finalization call and no health advancement, while other providers continue. Workflow concurrency serializes production runs; this is not an atomic cross-client reservation for separate audits or arbitrary operator processes. Those still require cadence coordination.

During recovery, the owner rearmed only the documented failure proven to occur before network access and preserved its failed run record. A subsequent real source-only attempt at **23:24:41 PDT / 06:24:41 UTC** skipped Jobicy and left source health unchanged. This is a narrow documented recovery, not permission to clear the cooldown after actual provider requests. The workflow is restored ACTIVE after its temporary repair pause.

Diagnostics contain controlled source status codes/text and aggregates, never user notes, tokens or full raw HTML. The public schema exposes no source-run diagnostics. Retention only removes obsolete source-run logs and unreferenced closed-job details after at least 90 days. Private history is never purged to save quota.

Owner control of releases and secrets is separate from public usage and billing. Writers can still run/cancel CI, public visitors can consume the service, and a budget notification need not enforce a hard cap. The approved configuration remains Free; Cloudflare's account billing API returned 403, so unrelated paid subscriptions were not verified. No universal zero-charge guarantee follows from these controls.
